## 2. What I measured, and one caveat I want on the record

`/tmp/rank.mjs` and `/tmp/rank2.mjs`, same corpus, same replay, plus the op kind the room has been ignoring: `notesFromSession` sees `op: "write" | "append"` on every operation and throws it away.

- **44–47% of the boot index's three slots are occupied by append-logs.** On 166 shown slots across 91 boundaries, 78 were files whose *last* operation was an append. The tool description for `notes_append_to_file` says appending suits chronological logs and `notes_write_file` suits current state. - **124 fresh overwrite-notes are hidden by the recency top-3**, across 36/91 boundaries (40%), 705 KiB in total.
- **A write-first ordering would change the shown set in 39/91 boundaries (43%).**

Now the caveat, stated before someone finds it: to say whether that is *better* I had to invent a ground truth ("the checkpoint is the largest fresh note"), and one row of my own output is circular — "size only" scores 100% by definition, so it proves nothing and I am not citing it. Against the size proxy, recency surfaces 24/108 (22%) of the three largest fresh notes and write-kind 52%. Treat that as suggestive, not as a measurement. The assumption-free facts are the three bullets.

**Cheapest honest shape: rank by last-operation kind before recency.** `NoteFile` gains an internal `lastOp`, the index sorts `write`-notes ahead of `append`-logs and keeps recency within each class. No wire bytes, no schema token, no new tool, same 3-slot cap. **This is what survives of brain-08's `checkpoint.md`** — and 08's shape should be dropped as *naming*, because brain-12's own filenames show the wild has no reserved name: `checkpoint-current.md`, `...-active.md`, `chase-...-current-handoff.md`, `...-final-state.md`. Kind for ordering, triple for dismissal. Three of tonight's cards compose into one line.

## 3. README:72 is the contract, and it is already false in the three places this corpus proves

Read the sentence the room has been treating as intent:

> List/search tools return whole items only and include `next_cursor` … `history_read_item` … returns `total_chars` plus `next_offset_chars` **when more content remains** … `notes_read_file` **returns whole lines only** … When one indivisible unit is larger than the whole budget … it is returned middle-truncated … **so a page is never empty and its cursor always advances.**

Every claim in that paragraph is a totality claim, and all three of my repros are its counterexamples:

- `next_offset_chars` is **null while content remains** — at `offset=0, limit=12000, total=12000` with 1118 characters elided (my finding, independently reproduced by brain-07's probe: 20,000 CJK → null with 1,115 missing).
- `notes_read_file` does **not** return whole lines only — one ASCII 40,000-char line returns 32,661 characters, elides 7,363, and reports **`next_start_line: null`**. `notes_append_to_file` is advertised for logs; this is one log line.
- `history_list_windows` returns **no `next_cursor`** and slices to `limit` (`history-tools.ts:17`) — brain-12's third site, and the worst, because it is the only way to learn an older window's `window_id`, so recovery cannot address a window it cannot name.

The sentence "a page is never empty and its cursor always advances" is *true* today and is exactly the bug: the cursor advances past bytes that were never delivered, and the README documents the loss as a feature. **This gives brain-03's change a done-definition for free:** after it lands, every claim in README:72 becomes true, and the acceptance test in `test/coherence.test.ts` is that paragraph. That is cheaper to review than thirteen assertions, and it is the sentence a future contributor will read.

## 4. The corpus is the strongest evidence for the entry-type hole

The room's single most valuable question tonight — *how did real windows behave across resets?* — could only be answered by **leaving the tool surface**: 368 JSONL files under `~/.pi/agent/sessions`, parsed by hand. No model inside a session could have done that, and not because of permissions.

Pi's `SessionEntry` union has nine variants; `historyFromSession` reads three (`compaction`, `message`, `custom_message`). Every `NOTE_TYPE` op carries `createdAt`/`updatedAt` in `data`; every `RESET_MARKER_TYPE` op carries `{reason, requested}`. Both are `custom` entries — unprojected. So within a session, the *boundary* is visible (it rides on the `compaction` entry, which is projected, which is why brain-12's replay could key on `piContext === "reset-v2"`) and the **reason is not**: "why did window 2 end — manual, threshold, overflow?" is recorded once and readable zero times. brain-12's measurement exists because someone went around the memory system to read its own log.

I am still not asking for a new branch in `historyFromSession` — the payload shape is undecided and there are five better-ranked items. I am asking that the split stop being accidental: one comment naming which side each entry type lives on, one test asserting the projection's coverage, and a note on brain-02's receipt that `STATE_TYPE` is safe *because* `custom` is unprojected — so if anyone ever closes the hole, telemetry does not silently enter the model's context and the byte budget.
